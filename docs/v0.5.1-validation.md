# v0.5.1: retained-state correctness and recovery acceptance

This page records the v0.5.1 contract. [v0.5.2](v0.5.2-acceptance.md) additionally
enforces typed per-window work, exact scenario-derived audit events and reconciled
component times. The retained-state/checkpoint invariants below remain unchanged.

## Why this patch exists

The v0.5 recovery coordinator checked active-event membership and cached facts.
A changed support count or total could therefore pass that check while the
current answer happened to remain unchanged. Snapshot decoding already checked
support consistency, but stop and cold-rebuild paths do not publish snapshots.
This was a verification gap, not evidence that historical answers were wrong.

The patch extends the recovery harness invariant, not the reasoning algorithm:

| Retained component | Required agreement with the current window |
| --- | --- |
| Active registry | Exact event IDs, plug identity and values |
| Aggregate entities | Exact key set, including complete removal after expiration |
| Support counts | Exact positive integer counts; booleans/floats are rejected |
| Support totals | Finite numeric totals, `rel_tol=1e-12`, `abs_tol=1e-7` |
| Materialised facts | Exact oracle facts and exact agreement with retained support |

The total tolerance matches schema-1 checkpoint validation and permits small
incremental floating-point drift. Checks never repair or recompute the maintained
total in place. A drift that changes the threshold classification still fails
exact fact agreement. The same checker covers normal updates, cold bootstrap,
replayed updates and loaded state at its recorded cursor. Invalid loaded state
becomes `checkpoint_rejected`; live-state divergence fails the experiment.

Full-window reference grouping is precomputed outside service/recovery component
timing. Comparisons against those references remain inside restore timing, as in
v0.5. Normal update validation remains outside maintenance timing. Checkpoint
serialization/decoding validation remains inside checkpoint I/O timing.

## Feasible-fixture acceptance gate

```sh
python experiments/run_v0_5_recovery.py --events 1000 --width 120 --slide 30 --flush --require-expected-outcomes --output-dir results/runs/validation-example
```

The gate independently derives expectations from the requested scenarios, query
schedules and retry budget; it does not infer them from observed outcome counts.
It requires all windows to fit the configured node. It accepts:

| Scenario | Stop baseline | Recovery policies |
| --- | --- | --- |
| No fault | `completed`, all windows served | `completed`, all windows served |
| Single fault, retries available | `stopped_on_failure`, only preceding windows served | `recovered`, all windows served |
| Single fault, zero retries | `stopped_on_failure`, only preceding windows served | `retry_exhausted`, only preceding windows served |
| Persistent fault | `stopped_on_failure`, one injected fault | `retry_exhausted`, retry budget consumed |

Expected faults and attempts also derive from the finite fault count: a recovery
policy injects at most `max_retries + 1` faults and attempts at most `max_retries`
recoveries. Persistent CLI scenarios request `max_retries + 1` faults.

For every workload/fault/policy key, the gate requires exactly one summary and an
ordered full detail trace. It validates status, failed window, requested/served/
unserved/checked queries, served-window prefix, fault/retry counts and valid
completed totals (terminal totals must be null). Detail counters must reconcile
with summary counters and every served window must have a checked state. Audit
evidence must contain each served window exactly once, the expected fault/retry
counts and terminal event, and consecutive per-case sequence numbers.

Missing/duplicate/unrequested cases fail. Swapping statuses between two cases
fails even if the global outcome histogram is unchanged. This is a regression
acceptance contract, not statistical performance acceptance or an SLA.

`acceptance.json` records expected and observed fields plus per-case mismatches.
The manifest records `acceptance_status=passed|failed|not_requested`; a requested
gate remains `pending` if configuration/execution fails before acceptance.
Results, audit and schedules are saved before acceptance. Failed acceptance
returns a non-zero exit code, retains the observed terminal outcomes and writes
a failed manifest hashing the report and other retained artifacts.

Without the flag, an experiment can validly report terminal capacity/checkpoint
outcomes with a passed execution manifest. Use this exploratory mode for capacity
sweeps; do not treat experiment completion as successful service. CI explicitly
enables the gate for its feasible recovery fixture and retains failure artifacts.

## Compatibility and scope

The runner retains its existing filename and arguments, adding one opt-in flag.
Its evidence milestone is now `v0.5.1`.
The previously stale package version is also corrected to `0.5.1`; the current
runner derives its milestone label from that version. Historical runner labels
remain unchanged. Policies, logical memory admission,
checkpoint schema 1, whole-trace identity and older strategy/placement experiments
are unchanged. Deterministic fields and checkpoint contents should replay exactly
within the same source/dependency environment; host timings need not match.

Audit events are still accumulated in memory and saved at experiment completion.
Fresh-process testing decodes a checkpoint; it does not resume streaming service
after an OS process is killed. Exact trace identity binds a fixed transition
sequence and changes when windows are appended. Hashes detect drift, not malicious
tampering. There is no deployed API, dashboard, agent evaluation or Jev integration.

A candidate v0.6 should first define process-resume, persisted input/service
cursors and incremental audit contracts. The MSAI application remains a separate
direction. This patch supplies stronger engineering evidence within the existing
KG repository without claiming the original P0–P4 agent roadmap is completed.
