# v0.6.1: process-resume integrity and failure evidence

This patch strengthens the v0.6 fixed-trace experiment without changing its
reasoning algorithm, request schedules, kill boundaries, restart policy or local
delivery claim. The v0.5 checkpoint codec, recovery policies and acceptance gate
remain separate baselines.

## Complete persisted-schema contract

The supported SQLite user version remains 1 with exactly `progress`, `receipts`
and `audit`, all STRICT, in DELETE journal mode. Validation compares the complete
generated table definitions, including primary keys, NOT NULL and CHECK
constraints. Whitespace and SQL keyword case differences are ignored; the table
and column inventories must also match their declared names/types exactly.
This is not a general SQL semantic-equivalence parser: alternate DDL, comments,
quoted identifiers, extra constraints/defaults and schema objects are rejected.
Column inventory and STRICT checks remain independent checks.

The progress row must independently contain integer `singleton=1`. Rejection
occurs before committing a new process-start or window record. SQLite's recovery
of a retained hot journal can occur on opening the database; this is not a
forensic promise that every rejected open leaves all on-disk bytes untouched.
The negative no-write tests use closed, non-hot fixture databases.

Checksums and schema validation detect accidental corruption/drift. They do not
authenticate a database or defend against an attacker with write access.

## Versioned engine identity

New job configuration identifies:

- `contract`: `fixed-trace-process-resume-v2`;
- `engine_fingerprint`: `utf8-crlf-to-lf-v1`;
- `engine_sha256`: hashes of the existing explicitly listed engine modules.

For engine identity only, each file must decode as UTF-8, CRLF becomes LF and
the resulting UTF-8 bytes are hashed. Lone CR, comments, spaces and all other
source edits are not normalized away. This is line-ending equivalence, not a
semantic Python-code equivalence claim. `.gitattributes` also specifies LF for
Python checkouts, but identity does not rely on users having that setting.

Run manifests continue hashing raw source/artifact bytes; immutable input/profile
hashes are also still raw. Equivalent LF/CRLF checkouts can therefore have equal
job identities but different raw provenance hashes. Oracle validation, explicit
source drift rejection and artifact checks are not bypassed.

### Compatibility

The v2 field set and identity algorithm are explicit. v1/v0.6.0 jobs and unknown
fingerprint algorithms are rejected before progress writes. There is no in-place
migration and no config/checksum rewriting. Continue an old job with its original
engine/environment, or reproduce its recorded input/profile/semantic arguments
into a fresh current-version job. This patch does not archive old engines or
guarantee migration across Python, SQLite or dependency versions.

SQLite user version 1 describes the unchanged storage layout. The job contract
version describes identity/validation semantics. The schema-1 checkpoint payload
codec does not change. These versions are not interchangeable.

## Bounded launch diagnostics

The supervisor drains stdout and stderr independently while waiting for a
rendezvous and process completion. Each stream retains at most 16,384 **bytes**
as a prefix, decoded as UTF-8 with replacement on invalid sequences. It records
total observed bytes, truncation and capture-error flags. This bounds retained
diagnostic memory without allowing a full stderr pipe to block the rendezvous.
It is not complete logging or secret redaction; the fixed worker is not a public
service and accepts no secrets. Failed diagnostics must still be handled as
potentially sensitive environment data.

Kill markers use duplicate-key/non-finite rejection and canonical typed JSON
comparison. Bool or float window indices, extra keys, oversized markers and
malformed JSON fail rather than triggering an accepted declared kill.

Unexpected outcomes raise `WorkerLaunchError` with an exportable record; timeout
also remains a `TimeoutError`. Records contain requested boundary, exit code,
failure category, bounded output and measured process wall time. Categories are
`spawn_error`, `child_exit`, `protocol_error`, `timeout`, `termination_error`,
`process_control_error`, `cleanup_error` and `capture_error`. They describe the
supervisor observation, not a complete business-error taxonomy. For example,
capacity rejection is a child exit with its diagnostic in stderr, not a
retryable resource failure.

Termination distinguishes normal exits, declared `parent_kill`, unexpected
`cleanup_kill` and spawn failures. Unexpected failures never join the expected
fault/restart acceptance protocol. The supervisor still bounds rendezvous and
completion waits separately, kills/reaps stuck children and stops the matrix.
The fixed worker creates no descendants; general process-tree supervision is
not implemented. Incomplete pipe capture is explicitly marked and cannot pass
as a successful launch.

`execute_case()` exports successful and failed launch records with `job_id` and
supervised `launch_number` (not the durable worker-attempt count). After the child
stops, offline validation provides a committed `cursor`, or `cursor=null` plus
`frontier_error` if validation fails. A missing/unvalidated frontier is never
invented from a cached value. Failed launch transcripts are exported before the
original error is re-raised. No new receipts/audit exports claim a failed job
completed.

## Matrix acceptance statuses

| Status | Meaning |
| --- | --- |
| `passed` | Every requested case ran and satisfied its expected prefix/protocol |
| `failed` | A complete evaluated gate found mismatches |
| `not_evaluated` | The full matrix was aborted by preparation, startup, timeout or another unexpected failure |

`pending` is only an in-memory running state, never a finalized failed manifest.
An aborted matrix writes `acceptance.json` with completed case results, expected
case count when known, aborted-case context and the error. Evaluated cases retain
their own passed/failed result; unrun cases are not fabricated as checked cases.
Partial summary rows and independently resumable jobs are preserved.

Exports/manifests still require the benchmark supervisor to survive. Parent
crash recovery, atomic export publication and evidence revisioning after manual
resume remain out of scope. SQLite is authoritative; historical bundle hashes
do not prove a manually continued job's new state.

## Verification and CI

New negative tests cover removed/altered PK, nullability and CHECK constraints,
invalid singleton, generated-DDL case/whitespace equivalence, LF/CRLF engine
identity, real source drift, unsupported old/fingerprint contracts, malformed
markers, large dual-stream output, spawn failure, both timeout stages, failed
frontier validation and partial-matrix diagnostics/hashes.

Existing first/last-window kills, stopped/resumed prefixes, bounded persistent
faults, idempotent completion, oracle checks and replay tests remain in place.
CI updates the existing v0.6 step to benchmark `v0.6.1` and output `v061`; it
introduces no package dependency, new job or changed v0.5 baseline.

No API, worker lifetime ownership enforcement, live inspector, dashboard, broker,
provider/agent integration, external exactly-once delivery or thesis application
is introduced. Those require separate approved contracts for v0.7 or later.
