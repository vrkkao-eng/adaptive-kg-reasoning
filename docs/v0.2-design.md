# v0.2 Design — Incremental Window Maintenance

## Research question

> **When a stream window advances, when is maintaining materialised knowledge cheaper than recomputing it from scratch?**

v0.2 moves from a static snapshot comparison to repeated window transitions. The aim is not to build a production RDF Stream Processing engine, but to create a controlled experiment in which additions, expirations, maintenance cost, and correctness can be measured explicitly.

## Core comparison

For each window transition `W_t → W_{t+1}`, compare two strategies:

### A. Full recomputation
1. Build the current window contents from the raw stream.
2. Recompute the relevant derived facts from scratch.
3. Replace the previous materialised dynamic state.

### B. Incremental maintenance
1. Identify events entering the window.
2. Identify events expiring from the window.
3. Update maintained aggregates / support state.
4. Add newly entailed dynamic facts.
5. Retract facts whose support no longer holds.

The two strategies must be evaluated on the **same sequence of windows**.

## Initial inference target

v0.2 should start with the existing semi-dynamic state:

```text
one-hour average load
→ HighRecentConsumption
```

This is preferable to starting with the 10-second overload rule because it produces enough overlap between adjacent windows to make incremental maintenance meaningful.

A later sub-experiment may add `CurrentOverload` as a highly volatile comparison.

## Window model

Initial controlled semantics:

- event-time ordered synthetic stream;
- fixed-width sliding window;
- fixed slide;
- deterministic event sequence;
- no out-of-order events in the first implementation;
- no late-event correction in v0.2.0.

Recommended defaults:

```text
window width: 3600 seconds
slide:        60 seconds
```

These defaults can later be parameterised.

## State model

Maintain explicit per-plug support state rather than recomputing all observations.

Minimum state:

```text
plug_id
active_event_count
sum_load
current_average
current_classification
```

For each transition:

```text
W_t
  │
  ├── expired events
  ├── added events
  ▼
update per-plug support state
  │
  ├── recompute affected averages only
  ├── add HighRecentConsumption where threshold is crossed upward
  └── retract HighRecentConsumption where threshold is crossed downward
  ▼
M_{t+1}
```

## Correctness criterion

The primary correctness invariant is **result equivalence**.

For every evaluated window:

```text
derived_facts_incremental(W_t)
==
derived_facts_full_recomputation(W_t)
```

Record:

- boolean equality;
- symmetric difference size;
- false additions;
- missed facts.

Any non-zero divergence is a correctness failure, not a performance trade-off, in v0.2.

## Metrics

Per window transition:

- `recomputation_ms`
- `incremental_update_ms`
- `speedup_ratio`
- `events_added`
- `events_expired`
- `affected_entities`
- `triples_added`
- `triples_retracted`
- `materialised_fact_count`
- `query_latency_ms`
- `state_memory_kib` or a clearly documented proxy
- `result_equivalent`
- `symmetric_difference_count`

Aggregate reporting:

- median
- p95
- mean
- total maintenance cost across the run

## Experimental factors

v0.2 should vary one factor at a time:

1. **Window overlap**
   - 3600/60
   - 3600/300
   - 3600/900

2. **Stream size**
   - 10k events
   - 100k events
   - later 1M events if runtime is reasonable

3. **Entity count**
   - number of houses / households / plugs

4. **Threshold crossing frequency**
   - stable loads
   - noisy loads
   - frequent spikes

This helps distinguish cases where incremental maintenance is valuable from cases where high churn reduces its benefit.

### `windows.py`
Responsibilities:
- ordered event iterator;
- sliding-window boundaries;
- additions / expirations;
- deterministic replay.

### `recompute.py`
Responsibilities:
- reference implementation;
- derive `HighRecentConsumption` from the full current window;
- prioritise clarity over speed.

### `incremental.py`
Responsibilities:
- maintain per-entity support state;
- process additions;
- process expirations;
- generate additions / retractions in materialised facts.

### `metrics.py`
Responsibilities:
- timing;
- memory/proxy measurement;
- equivalence checks;
- aggregate summaries.

## Test plan

### Window mechanics
- event enters exactly once;
- event expires exactly once;
- boundary timestamps are deterministic;
- no event is simultaneously missing from both previous and current state without explanation.

### Incremental additions
- crossing the threshold upward creates one `HighRecentConsumption` fact.

### Retractions
- when supporting observations expire and the average falls below threshold, the fact is removed.

### Result equivalence
For every window in a deterministic fixture:

```python
assert incremental_facts == recomputed_facts
```

### Idempotence
Replaying the same transition must not duplicate facts or double-count support state.

## Milestones

### v0.2.0 — window mechanics
- deterministic sliding windows;
- additions / expirations;
- tests for boundary behaviour.

### v0.2.1 — recomputation baseline
- full-window reference derivation;
- per-window benchmark output.

### v0.2.2 — incremental maintenance
- maintained support state;
- additions and retractions;
- strict equivalence tests.

### v0.2.3 — comparative benchmark
- compare full recomputation and incremental maintenance;
- report median / p95 cost and total run cost;
- document where incremental maintenance helps or does not help.

## Scope boundaries

v0.2 will **not** claim:

- a complete RDF Stream Processing engine;
- general incremental OWL-RL truth maintenance;
- support for arbitrary SPARQL continuous queries;
- distributed / edge execution;
- out-of-order or late-event semantics;
- a production-grade truth-maintenance system.

The experiment is deliberately narrower: it isolates the cost and correctness of maintaining one transparent window-dependent materialised state.

## Success criteria for v0.2

v0.2 is complete when:

1. the same deterministic stream can be replayed through repeated sliding windows;
2. additions and expirations are explicit and auditable;
3. incremental maintenance supports both addition and retraction;
4. every incremental result matches full recomputation;
5. benchmark output shows where maintenance cost is lower, equal, or higher than recomputation;
6. CI runs correctness tests and at least one small benchmark smoke test.

## Link to later versions

v0.2 provides the update-cost term needed by v0.3.

Conceptually:

```text
materialisation utility
=
future query reuse benefit
- initial inference cost
- update / maintenance cost   ← measured in v0.2
- memory cost
```

Only after v0.2 provides a trustworthy maintenance-cost baseline should v0.3 introduce an adaptive materialisation policy.
