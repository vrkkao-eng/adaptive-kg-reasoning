# v0.5: bounded recovery of incremental KG state

## Operational question

Can a fixed site's window-dependent KG state recover from a worker crash while
preserving the same answers, and what work does recovery add? v0.5 makes that
contract executable with real local checkpoint files and deterministic worker
fault injection. The v0.4 placement experiment remains a separate baseline.

## Comparison contract

All three policies receive the same ordered input, windows, threshold, query
schedule, fixed node profile and fault scenario:

| Policy | On an injected crash | Normal-path checkpoint cost |
| --- | --- | --- |
| `stop_on_failure` | Stop service at the failed window | None |
| `cold_rebuild` | Discard state and rebuild from the current window | None |
| `checkpoint_replay` | Discard state, load the latest checkpoint and replay subsequent transitions | Actual local write/fsync/replace cost |

Without a published checkpoint, `checkpoint_replay` explicitly cold-starts from
the current window and records `reason=no_checkpoint`. A present but invalid
checkpoint is rejected without falling back to cold rebuild. This distinction
keeps a broken recovery assumption visible.

The node is declared with `--node` before evaluation and remains fixed; the
default is fog. Admission uses v0.4's logical retained-memory model and the
current window's reference cardinalities. A capacity violation is terminal for
every policy. Restarting cannot repair an insufficient budget. This is harness
admission accounting, not physical memory enforcement or a placement optimizer.

## Window and fault sequence

```text
admit current window
  -> before_update fault point
  -> apply transition and check state
  -> after_update fault point
  -> publish checkpoint when due
  -> after_checkpoint fault point
  -> read, check and serve current queries
```

The recovery coordinator and request schedule survive an injected worker
exception; the worker's in-memory state is discarded. Checkpoint decoding is
also tested in a fresh Python process. The experiment does not terminate an OS
process or test coordinator failure.

`after_checkpoint` targets a checkpoint boundary. For policies without disk
checkpoints, the same fault occurs after state validation at the equivalent
pre-query stage. Checkpoints occur at indices divisible by `checkpoint_every`,
including index 0, and store the last applied window cursor. A crash after
publication may therefore restore the current window directly without applying
its deltas twice. Restored cursors before the current window replay through the
preceding window, then apply the current one. Historical queries are not replayed.

Each failed window allows at most `max_retries` recovery attempts beyond its
initial attempt. The default single crashes happen once; `persistent_crash`
injects `max_retries + 1` failures after update to demonstrate exhaustion.
Zero retries is supported. Terminal outcomes stop all later service, including
when state subsequently shrinks. There is no infinite loop or automatic resume.

The coordinator counts current queries as served only after the state and
answers pass independent oracle checks. Worker replay does not serve the same
window twice. This is a local harness invariant, not an end-to-end exactly-once
delivery guarantee: acknowledgments, external side effects and the coordinator's
served cursor are not durably persisted with the worker checkpoint.

## Checkpoint format and publication

Schema version 1 stores a payload and its SHA-256 checksum. The payload contains
the applied-window cursor, trace identity, threshold, active-event registry,
per-plug support counts and floating-point totals, and materialised facts.
Restoration preserves original aggregate totals rather than silently changing
floating-point history by recomputing them.

Trace identity hashes the exact window transitions and the semantic configuration
`highrecent-incremental-v1` plus threshold. Changed input, deltas, boundaries or
threshold invalidate identity. The runner derives this identity independently
from its current trace, never from the checkpoint it is validating. The format
also rejects unknown schemas, duplicate JSON keys/events/facts, malformed URIs,
non-finite values, inconsistent counts/totals/facts and invalid cursors. A small
documented tolerance (`rel_tol=1e-12`, `abs_tol=1e-7`) allows incremental
floating-point roundoff when checking totals against active-event support;
fact equivalence itself remains exact.

Publication writes a temporary file in the destination directory, flushes and
fsyncs it, then atomically replaces the previous file with `os.replace`. A failed
replace preserves the old checkpoint and cleans the temporary file. The
experiment uses unique run directories and checkpoint paths; normal publication
within a run updates only its known checkpoint file.

This tests local file integrity and atomic replacement. Directory fsync,
power-loss durability across platforms, concurrent writers, remote object
storage and malicious tampering are outside the contract. The checksum is not
authentication. Loading requires a matching trace identity and validates
support state; the coordinator additionally checks the cursor, threshold,
active events and facts against the corresponding reference window.
As of [v0.5.1](v0.5.1-validation.md), coordinator checks also compare aggregate
entity keys, counts and finite totals against independently precomputed support;
the same invariant applies to normal, cold-bootstrap and replayed updates.

## Failure and timing accounting

| Outcome | Meaning |
| --- | --- |
| `completed` | All windows served without an injected crash |
| `recovered` | All windows served after one or more bounded recoveries |
| `stopped_on_failure` | Stop baseline reached an injected crash |
| `retry_exhausted` | The failed window consumed its retry budget |
| `checkpoint_rejected` | A present checkpoint failed recovery validation |
| `memory_budget_exceeded` | Declared retained-state admission failed |

Semantic divergence, invalid configuration/input and unexpected I/O/application
errors fail the experiment and retain a failed manifest. Expected terminal
policy outcomes can coexist with a `passed` experiment manifest, because the
harness successfully verified that behavior. Inspect `recovery_outcomes` and
unserved queries rather than treating manifest success as service success.
The optional v0.5.1 `--require-expected-outcomes` gate distinguishes execution
completion from acceptance of each feasible-fixture service outcome. CI requires
this gate and retains `acceptance.json`, including on failure.
The [v0.5.2 acceptance patch](v0.5.2-acceptance.md) checks typed per-window work,
declared audit protocol and timing reconciliation without changing these policies.

Unlike v0.4's simulated milliseconds, v0.5 measures actual host component time:
maintenance (including failed attempts and replay), query readout, checkpoint
publication and checkpoint loading/validation. Independent oracle computation,
normal state/answer validation, trace hashing, fault injection and audit logging
are outside component timing; checkpoint serialization/support validation are
inside publication timing. Restore validation is inside restore timing.

`measured_work_ms` sums these disjoint components even for incomplete runs;
`measured_total_ms` is null for terminal outcomes. The summary retains requested,
served and unserved queries, served windows, fault/retry counts, update calls,
cold bootstraps, replayed windows, checkpoint writes/loads and cumulative bytes
written. `recovery_apply_ms` is a subset of maintenance time;
`measured_recovery_ms` adds that subset to restore time and excludes subsequent
checkpoint publication. Neither subset should be added again to the total.
The `replayed_windows` work counter includes the recovering current transition
when it is applied. `window_replayed` audit events describe historical transitions
before that current window; they are not one-for-one with the work counter.
These timings exclude backoff, failure detection, scheduling and network costs
and therefore do not establish an RTO, SLA or end-to-end downtime.

Oracle checks count actual validation work per policy/attempt, including replay
and restored states. They are not unique windows across the experiment.
Served queries are checked once per successful window and policy. Query readout
is the existing fact-tuple proxy rather than an API or SPARQL endpoint.

## Evidence and verification

Each fresh bundle contains copied input/profiles, `workloads.json`,
`detail.csv`, `summary.csv`, ordered `audit.json`, latest per-case checkpoint
files and `manifest.json`. The manifest fingerprints all retained files and
the source/configuration. Audit sequences expose faults, retries, restoration
cursors, replay, explicit cold start, publication and service/terminal outcomes.
Superseded checkpoints are not archived; cumulative written bytes still include
all successful publications.

The default matrix has four workloads, five fault scenarios and three policies:
60 independent policy cases. All policies execute on the same host; fixed policy
order and OS cache effects limit timing comparisons. No universal checkpoint
speedup is claimed. Vary checkpoint cadence and stream overlap to inspect costs.

Tests cover state preservation and post-restore expiration, all crash boundaries,
current-window checkpoint restoration, no-checkpoint cold start, bounded repeated
failure, corrupt/mismatched/truncated snapshots, replacement failure, resource
exhaustion, oracle divergence, fresh-process decoding and deterministic bundle
replay. CI executes the recovery matrix and preserves its artifacts with the
existing benchmarks. See [replay instructions](reproducibility.md).
The v0.5.1 regressions additionally cover corrupted live support with unchanged
cached facts, roundoff/threshold boundaries and per-case acceptance/accounting.

## Next boundaries

This milestone supplies recovery evidence for one maintained KG state. Durable
query acknowledgment, write-ahead logging, remote workers, migration, late
events, production APIs, security controls and agent/LLM integration require
separate contracts and evaluation. The MSAI thesis demonstration remains a
separate application direction.
