# v0.7.0: bounded fixed-trace job operation

## Outcome and scope

The business problem remains repeated queries over changing KG windows. This
milestone makes the existing correctness-checked worker operable through local
HTTP. The evidence chain becomes problem → contract → comparative baselines →
oracle checks → process recovery → packaged HTTP operation → container restart.
A successful HTTP response alone is not acceptance.

The contract is one host, local storage, one controller and one execution slot.
Clients use the packaged deterministic `demo` fixture and bounded parameters,
not paths, URLs, executables, credentials or retry policies. Defaults produce
seven windows and 56 dense requests. Node profiles remain illustrative logical
resource budgets, not distributed edge/fog/cloud execution.

## Ownership and durable intent

```text
HTTP + durable idempotency key
  → registry.sqlite: reservation, lifecycle, attempt token, operational events
  → worker: execution.lock + worker.lock
  → progress.sqlite: atomic KG state + input/service cursors + local receipts
  → evidence/<attempt>: immutable checked snapshot + hash manifest
```

The controller holds `service.lock` for its lifetime. A worker holds the global
execution slot through execution, snapshot and lifecycle finalization. The core
worker holds its per-job lock before loading/validation until execution ends,
including direct process-resume calls. Locks use Windows byte-range locking or
POSIX `flock`, are non-blocking and released by death. Never unlink/reclaim lock
files by PID. NFS, multiple hosts and arbitrary direct database writers are
unsupported; `ResumeStore` itself is not a concurrent service API.

Reservation precedes directory creation; durable start intent precedes child
creation. A child must own the slot and match its attempt token before running.
Restart cannot steal a live orphan's lock. With no owner, reconciliation validates
the prefix, revokes the token and requires explicit resume; delayed stale children
cannot commit. Locally known not-yet-owned children are not prematurely reclaimed.
Termination of owned processes handles Windows Python redirector descendants,
not unrelated PIDs; restarted controllers never kill/adopt orphan processes.

| State | Meaning / restart behavior |
| --- | --- |
| `preparing` | Key reserved; interrupted preparation fails closed |
| `created` | Prepared job; explicit resume after controller restart |
| `starting` | Token/intent persisted; no-owner reconciliation validates prefix |
| `running` | Live worker/orphan; no additional worker |
| `interrupted` | Recoverable prefix; explicit bounded resume |
| `completed` | Complete committed prefix; resume does not launch/rewrite progress |
| `failed` | Terminal failure; no repair or automatic retry |

Keys are ASCII `[A-Za-z0-9_.-]`, 1–64 characters; only SHA-256 digests persist.
Normalized equivalent requests return the same job; changed parameters return
409. Repeated submission never implicitly resumes interruption. Limits are 64
retained jobs and three launch intents per job, including failed process creation.
No deletion API means keys remain durable for the root lifetime. Default attempt
timeout is 60 seconds. Workers also check their deadline at application boundaries.
A restarted controller cannot forcibly time out an orphan stuck outside those
boundaries; hard orphan supervision is not implemented.

## Read model, metrics and evidence

Status reads use read-only SQLite snapshots checked against cached job metadata:
identity, coupled frontiers and receipt-prefix accounting, without rebuilding the
oracle per poll. Lifecycle state and `committed_complete` are separate: the final
commit can precede evidence/lifecycle completion. These reads are not forensic
validation; full schema/support/oracle checks occur on preparation, owned resume,
reconciliation and export. A read-only connection cannot recover a hot journal;
temporary 503 responses are allowed until controlled owned recovery.

Receipts/events are paginated to 100 items. Events correlate server request UUIDs,
job UUIDs and attempt tokens. Window events are separate from KG transactions:
death after commit can omit an event. Receipts, not event counts, are authoritative.
Metrics provide bounded state labels, durable launch-intent counts and committed
window/query gauges, without per-job labels. `checked_window_wall_ms` includes
oracle checks and serialization, not pure update latency or an SLO. No backend,
dashboard, distributed traces or full OpenTelemetry instrumentation is claimed.

Cooperative attempts publish input/config, state, receipts, audit and summary with
hashes/runtime fingerprints. Reconciliation attempts a stopped-prefix snapshot
before resume. Directories are never overwritten; a missing final manifest means
incomplete export, recorded as `evidence_complete=false`. The live progress store
is mutable; immutable snapshots preserve earlier prefixes. Locally owned children
also retain bounded output/exit diagnostics. None of these exports or HTTP
acknowledgments are part of the KG commit transaction. Hashes detect drift, not
malicious tampering; this is not signed audit storage.

## Compatibility and claim boundaries

Registry schema 1, contract `fixed-trace-job-service-v1`, binds a root to exact
Python/SQLite, selected dependency versions and normalized engine/service hashes.
Drift fails startup; no automatic migration. Process-resume v2 and progress
schema 1 remain, but lock code is now an engine fingerprint input. Old jobs need
their original environment or fresh reproduction; never rewrite identity fields.
Tested dependency constraints are not a cryptographic lockfile.

No external exactly-once delivery, append-only stream, broker, authentication,
multi-tenant isolation, power-loss test or public production deployment is added.
Jev remains a future provider/baseline within this repo if a separate agent track
is approved; ReAct, RAG answer evaluation and the MSAI application are not scope.
See [operations](operations.md), documented
[FastAPI lifespan](https://fastapi.tiangolo.com/advanced/events/),
[POSIX locks](https://docs.python.org/3/library/fcntl.html) and
[Windows locks](https://docs.python.org/3/library/msvcrt.html).
