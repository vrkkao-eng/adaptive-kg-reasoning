# v0.6.0: fixed-trace process resume

## Operational problem and comparison

v0.5 keeps its coordinator alive while a worker raises an exception. v0.6 tests
the next boundary: terminate the entire Python worker from its parent and open
the same persisted job in a fresh Python process. No worker memory survives.
The immutable input, engine/config identity and SQLite progress file do survive.

Each workload compares uninterrupted execution with stop and resume policies at
four kill boundaries. A persistent before-commit case exercises bounded restart
exhaustion. Four workloads and ten scenarios produce 40 cases by default.
All use the existing incremental KG semantics and full-window correctness oracle.

| Boundary | Committed frontier after a kill at window i | Resume action |
| --- | --- | --- |
| before update | i - 1 | Apply/check window i again |
| after update, before persistence | i - 1 | Discard lost worker memory; apply/check i again |
| before commit, after transaction writes | i - 1 | SQLite rolls back; apply/check i again |
| after commit, before worker completion output | i | Restore i; begin at i + 1 |

The parent waits for an explicit stdout rendezvous, then calls `Popen.kill()` and
reaps the non-successful process. There is no sleep-based race or graceful worker
cleanup. Windows uses process termination; POSIX uses SIGKILL. A fresh child
performs every restart. Rendezvous and completion waits are bounded to 60 seconds;
the parent kills/reaps a stuck worker and fails the experiment.
Kills occur at declared application boundaries, not random instructions within
SQLite's internal commit code. System/power failures are not injected.

## Persisted identity and cursors

Each fresh job directory contains `input.csv`, `profiles.json`, `job.json` and
`progress.sqlite`. Initialization refuses an existing directory. A resume never
creates a missing database or changes configuration to make old state fit.

Job identity binds exact input/profile bytes, window width/slide/flush, threshold,
workload/query schedule, fixed node, complete window trace and hashes of the
specified engine modules. A new worker derives identity independently, then
validates stored identity, schema, receipts, audit and snapshot support state.
Changed files/configuration/source require a new job, not an in-place migration.
This strict fingerprint deliberately permits no online append to the input.

Three frontiers are persisted in the same transaction:

- `input_cursor`: count of filtered load events admitted through this window's
  additions; a fixed-trace offset, not an original CSV byte or broker offset;
- `applied_cursor`: last committed zero-based KG window, initially -1;
- `served_cursor`: last locally committed window receipt, also initially -1.

Applied and served cursors are equal here because an entire window batch commits
together. The input count may stay unchanged while later windows expire events.
All cursors and receipt counts are checked against independently rebuilt windows.

## Transaction and delivery boundary

SQLite uses rollback-journal (`DELETE`) mode and `synchronous=FULL`; STRICT tables
require SQLite 3.37 or newer. It is Python's standard-library backend, not a new
package dependency. The runtime SQLite version is recorded in the manifest.

```text
immutable input/config -> reconstruct trace and check persisted prefix
  -> restore retained KG state -> apply next window -> oracle/state/query checks
  -> BEGIN IMMEDIATE
       update state snapshot + checksum + all three frontiers
       insert unique window receipt + result digest
       insert incremental window_committed audit event
     COMMIT
  -> next window (or completion output)
```

A separate committed `process_started` audit record captures each unfinished
process attempt and its initial frontier. State, receipt and the corresponding
window audit event then commit together. The schema-1 snapshot payload codec is
reused; v0.5 file checkpoint format/policies remain unchanged. A stale writer
cannot commit a window whose preceding frontier has already advanced. This is
not a multi-writer service: run one worker per job, and inspect/hash its evidence
only after workers stop.

SQLite provides the transaction mechanism; see its primary documentation on
[atomic commit](https://www.sqlite.org/atomiccommit.html) and
[synchronous settings](https://www.sqlite.org/pragma.html#pragma_synchronous).
These experiments prove the observed local process-kill/reopen behavior, not
hardware-independent power-loss durability or correctness of every filesystem.
Retain any SQLite rollback journal together with its database if interruption
leaves one; let SQLite recover it rather than deleting it manually.

`served_queries` means **oracle-checked queries represented by locally committed
receipts**, not acknowledgments delivered to an external client. Reads computed
before an uncommitted crash may execute again. No network response, tool side
effect or client acknowledgment is inside the SQLite transaction. The unique
window receipt and cursor prevent duplicate *local accounting*, not universal
end-to-end exactly-once delivery. A zero-query window still commits checked state.

## Validation and failure handling

On startup, receipts must form the exact contiguous committed prefix with the
declared query counts, input offsets and oracle result digests. Audit sequences,
attempt numbering, start frontiers and commit events must match that prefix.
The snapshot checksum, cursor, threshold, active events, aggregate keys/counts/
totals and exact facts are checked. Validation never repairs mismatched evidence.
Hashes are integrity checks, not authentication or tamper-evident security.

The supervisor's acceptance projection derives expected committed frontiers,
process starts and ordered commits from the declared fault, policy and restart
budget. It checks every observed post-termination frontier and final service
prefix. The worker/store also validate receipt answers against full recomputation.
First/last-window faults, zero restarts and after-final-commit restart are tested.
Completed resume is a validated no-op: it changes neither receipts/audit nor DB.

`max_restarts` counts new launches after the first killed attempt. Persistent
before-commit faults cause at most `max_restarts + 1` killed processes, retain
the last committed prefix and report `restart_exhausted`. Stop reports
`interrupted`; successful recovery reports `resumed`; no-fault reports `completed`.
These are process outcomes: a kill after the last commit may be interrupted with
all local receipts present. Always inspect frontiers and unserved counts too.

Invalid identity/schema/state, failed resource admission, I/O errors, unexpected
child exits/timeouts and semantic divergence fail the matrix with a non-zero
exit and a failed manifest. They do not silently cold-rebuild or bypass windows.
Resource admission is the unchanged logical retained-memory model, not physical
enforcement. Infeasible profiles are not accepted by this feasible-fixture gate.

## Evidence and measurement

The top bundle contains input/profiles, evolving `summary.csv`, `acceptance.json`
and a manifest with recursive artifact/source hashes. Each nested job retains its
own inputs/config/DB, `supervisor.json` (launch exits, stdout/stderr, frontiers and
wall times), `receipts.json` and `audit.json`. Terminal and gate-failed results are
retained. Startup/timeout failures retain the failed manifest and partial jobs;
only successful supervised launch records are exported to the transcript.
The authoritative progress is SQLite, not an export or the parent run manifest.
Exports and manifests are finalized by a surviving benchmark supervisor; their
own crash recovery is not claimed. A prepared job can resume without that parent.

`process_wall_ms` includes child launch, re-derivation/oracle validation, SQLite
I/O and termination/reaping overhead. It is not v0.5 component timing, a speedup,
RTO, downtime measurement or SLA. Incomplete runs retain partial wall work. Do
not compare it to a completed total as if they served the same workload.

Replay should match non-timing summary fields, acceptance, receipts and audit.
Raw SQLite bytes, exit-code conventions, transcript timings and host metadata
are not a cross-platform deterministic artifact contract.

## Commands and boundaries

```sh
python experiments/run_v0_6_resume.py --events 300 --width 120 --slide 30 --flush --output-dir results/runs/resume-example
python experiments/resume_worker.py --job-dir results/runs/resume-example/dense-before_commit-stop
```

The second command continues that stopped job from its committed frontier.
An earlier manifest describes an earlier evidence snapshot: manually continuing
a job changes its DB, so its historical hashes/exports must not be treated as a
fresh completed bundle. Use a new matrix directory for reproducible comparisons.

CI retains the existing v0.5.2 matrix and adds a bounded 300-event v0.6 matrix;
all evidence is uploaded by the existing job. No provider/Jev, agent workflow,
dashboard, production API, remote storage, broker offset, migration, security
control or MSAI thesis application is introduced. A live deployment and external
delivery contract remain separate future milestones.
