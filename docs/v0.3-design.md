# v0.3 — cost-aware materialisation of one derived state

## Problem and success criteria

A changing knowledge graph serves repeated requests for `HighRecentConsumption`.
Retaining that result can save repeated scans, but consumes support state and
maintenance work even while nobody queries it. Which choice is worthwhile as
demand and window overlap change?

Acceptance requires identical answers for every requested window, measured and
modelled cost reported separately, no access to future query counts by the policy,
and auditable decisions including rebuild cost. Adaptive need not win. In
particular, delayed demand prediction can waste work during bursts.

## Common workload and baselines

All four strategies receive the same ordered, finite, load-only events, window
sequence, threshold and full-result query schedule. Repetitions reset all strategy
state; a seeded shuffle changes strategy execution order within each repetition.
Input loading/window construction, oracle checks, telemetry and serialization are
harness work outside the reported strategy timings. This is an in-process
benchmark, not an API latency, SPARQL or end-to-end ingestion measurement.

| Strategy | Window maintenance | Request execution |
| --- | --- | --- |
| `recompute` | Full recomputation every window, including idle windows | Consume cached full result |
| `query_time` | No derived-state maintenance | Recompute and consume full result on every request; no memoization |
| `incremental` | Full initial bootstrap, then apply every delta | Consume cached full result |
| `adaptive` | Choose query-time or incremental before seeing current demand | Same selected implementation as fixed baselines |

v0.1 static materialisation numbers and v0.2 maintenance-only numbers are retained
as historical experiments, not mixed into these v0.3 comparisons.

Workload schedules: `none` has no requests; `sparse` has one every eight windows;
`dense` has eight each window; `bursty` alternates eight busy and eight idle windows.
The harness knows the schedules; the policy sees only the previous window's count.
These are synthetic workloads, not claims about a production demand distribution.

## Decision model

Let `N` be current active load events, `D` entering+expiring events, `Q` previous
window query count, and `F` the last observed result size (initially zero).
Coefficients are `e=1` per processed event, `r=0.05` per returned fact,
`m=0.02` per retained support-event/fact per window, and `s=1` per
incremental-state allocation/release. They are explicitly **synthetic cost units**;
they are neither fitted runtime costs nor currency. CLI `--memory-price` varies m.

```text
query-time estimate = Q * (N*e + F*r) + (s if state retained else 0)
incremental estimate = (D if state retained else N)*e
                     + Q*F*r + (N+F)*m + (0 if state retained else s)
utility = query-time estimate - incremental estimate
```

Select incremental only when utility is strictly positive; ties choose query-time.
There is no hidden warm incremental state in query-time mode. Re-entry rebuilds
from all current events, not just the most recent delta. The first prediction is
zero. No hysteresis or future-window lookahead is implemented; oscillation and
forecast lag are visible in the trace. Memory price is a soft objective, not a
hard memory limit. High churn may make incremental unattractive even when retained.

`realized_model_units` substitutes actual event work, current requests/results,
retained items and allocation/release into the same model. Recompute retains only
result facts; incremental retains support events and facts; query-time retains
neither. The shared input windows are excluded. This simplified model omits
container overhead, per-plug aggregate objects, snapshot copying, scheduling and
decision overhead. Those implementation costs can affect wall-clock performance;
model-unit improvement does not establish runtime improvement.

## Measurements and correctness

Per-window trace includes predictions, both estimated costs, selected mode/reason,
switches, actual requests, event work, result size, retained items, and:

- `bootstrap_ms`, including creation and application of a full bootstrap;
- `maintenance_ms`, including apply/recompute and result snapshot creation;
- `release_ms`, releasing the retained incremental state;
- `query_ms`, all request executions and identical full-result consumption;
- `decision_ms`, adaptive selection itself;
- `total_ms`, sum of those five measured components;
- a Python retained-state size proxy, not process RSS or peak transient memory.

For each strategy the full recomputation oracle is computed independently outside
timed blocks. Every query answer must exactly match it. Materialised state is also
checked on windows without queries. An idle query-time window has no answer to
validate: `state_checked=false`, `checked_queries=0`, `result_count=null` (blank in
CSV). Never describe that as an answered query. Divergence raises and the runner
records failure; it is not exchanged for a speed improvement.

## Reproduce

```sh
python -m pytest -q
python experiments/run_v0_3_policy.py --events 5000 --seed 42 --repetitions 3 --output-dir results/runs/policy
python experiments/run_v0_3_policy.py --input results/runs/policy/input.csv --seed 42 --memory-price 1 --output-dir results/runs/high-memory-price
```

Each run uses the v0.2.4 manifest and artifact hashes plus `workloads.json` and
recorded execution order. `summary.csv` has one row per strategy/scenario/workload/
repetition. Inspect distributions and component costs, not only the best run.
CI gates correctness/contract invariants, not wall-clock speedup thresholds.

## Scope and next step

One state family and one query type; no per-entity selection, learned cost model,
hard memory budget, distributed execution, late-event correction, LLM or agent.
The existing v0.2 numerical aggregation semantics are preserved. Robust handling
of extreme floating-point inputs and calibrated cost prediction are future work.
v0.4 can add placement/network constraints once this local cost accounting is
adequate; those costs must be reported as simulated until measured on real nodes.
