# v0.4: resource-aware fixed placement

## Question and scope

Where should a dynamic KG's maintained `HighRecentConsumption` state reside
when compute rates, retained-memory budgets, source location and client location
differ? Preserve exact answers while exposing the resource trade-off and the
consequences of an inaccurate workload estimate.

This version is a deterministic service-demand simulator around the existing
incremental implementation. It does not deploy workers, enforce physical memory
limits or measure network traffic. It holds the reasoning strategy constant:
v0.3's materialisation policy is not combined with placement in this experiment.

## Execution contract

1. Validate and copy the profile into a fresh evidence bundle.
2. Score all nodes using only the declared workload estimate; persist the
   decision before generating or reading the evaluation stream.
3. Build common windows and query schedules. Execute incremental maintenance
   once per window/workload on the host and check every state and query against
   independent full recomputation.
4. Apply each node's resource/network model to that shared reference trace.
5. Report the three fixed baselines and the preselected baseline's outcome.

`budget_aware` references a fixed candidate's result. It does not execute a
fourth copy or multiply correctness-check counts. Placement scenarios likewise
share reference execution; only the source/client/resource accounting differs.
The oracle, serialization and cost-model evaluation are outside reference timings.

## Profiles and units

[`configs/placement_profiles.json`](../configs/placement_profiles.json) uses
schema version 1 and exactly five top-level fields: `schema_version`, `nodes`,
`links`, `memory`, `scenarios`. Nodes must be `edge`, `fog` and `cloud`, each once.
Scenario names are unique; all required direct links must exist. Costs must be
finite and non-negative, budgets/counts non-negative integers, bandwidth and
payload estimates positive. Invalid profiles fail the run with a manifest.

| Component | Declared fields | Meaning |
| --- | --- | --- |
| Node | `memory_budget_bytes`, `update_ms_per_event`, `refresh_ms_per_entity`, `read_ms_per_fact`, `query_base_ms` | Logical capacity and illustrative compute coefficients |
| Link | `a`, `b`, `rtt_ms`, `bandwidth_bytes_per_second` | Symmetric direct link; bytes/sec, not bits/sec |
| Memory | `base_bytes`, `bytes_per_event`, `bytes_per_entity`, `bytes_per_fact` | Logical retained-state accounting |
| Scenario | `name`, `source`, `client`, `estimate` | Ingress and query endpoints plus a planning forecast |

For each window, with additions A, expirations E, affected entities U, queries Q
and result facts F:

```text
compute_ms = (A + E) * update_ms_per_event
           + U * refresh_ms_per_entity
           + Q * (query_base_ms + F * read_ms_per_fact)

retained_bytes = base_bytes + active_events * bytes_per_event
              + active_entities * bytes_per_entity + F * bytes_per_fact

remote_ingress_ms = RTT / 2 + batch_bytes / bandwidth_bytes_per_second * 1000
remote_query_ms   = RTT + (request_bytes + response_bytes)
                         / bandwidth_bytes_per_second * 1000
total_ms = compute_ms + ingress_ms + Q * remote_query_ms
```

Local transfers cost zero. An empty ingress batch costs zero. Each remote query
pays one RTT, including an empty answer. Links have no multi-hop routing,
concurrency, queueing, retries, packet headers, TLS, compression or contention.
The sum is serialized service demand, **not** measured elapsed time, throughput,
SLA latency or a scheduling simulation. It must not be added to v0.3's synthetic
cost units or to measured host timings.

Actual evaluation payload sizes use compact sorted-key UTF-8 JSON. Ingress is
one array of newly added event records per nonempty window transition, not a
resend of the complete overlapping window. Expiration is deterministic and
local, so it incurs compute but no transport. A query request is the constant
`{"query":"HighRecentConsumption"}`; its response is a sorted array of string
triples, with `[]` occupying two bytes. This wire representation is an explicit
model, not an implemented network protocol.

Memory counts the post-transition retained state. It excludes shared harness
inputs, source buffers, Python/RDFLib overhead and transient update/serialization
allocations. It is neither measured RSS nor a bound on peak physical memory.

## Planning versus evaluation

The estimate declares `windows`, `active_events`, `distinct_entities`,
`added_events`, `expired_events`, `affected_entities`, `queries_per_window`,
`result_facts`, `event_payload_bytes` and `fact_payload_bytes`.
Queries may be fractional expected demand. Counts describe a constant expected
state after bootstrap, not future observations or a guaranteed maximum.

Bootstrap charges all estimated active events and distinct entities. Remaining
windows charge estimated additions, expirations and affected entities. All
windows charge estimated query demand. Estimated response bytes are
`2 + result_facts * fact_payload_bytes`; the per-fact estimate includes its wire
contribution. Estimated ingress bytes are event count times its byte estimate.
These are forecasts, not exact serialization sizes.

Reject nodes whose estimated retained state exceeds their budget; choose the
remaining node with minimum estimated total cost across the declared horizon.
Ties use lexical node name, independent of profile order. If none qualifies,
report `no_feasible_estimate`, no selected node and no cost/served work.

The sample scenarios deliberately illustrate distinct decisions:

| Scenario | Source / client | Selected from estimate | Key factor |
| --- | --- | --- | --- |
| `edge_local` | edge / edge | edge | Local traffic under a small forecast |
| `fog_budget` | edge / edge | fog | Larger forecast excludes edge |
| `cloud_client` | edge / cloud | cloud | Client proximity and compute rates |

These illustrative profiles are not calibrated or learned from the benchmark.
Evaluation input, window sizes and query schedules can differ from the forecast.
No decision is retuned after seeing evaluation results; no claim is made that
the selected site always wins or remains feasible.

## Failure semantics

Each fixed site admits a window only when its modeled retained bytes fit.
At the first violation, service stops for that window and the remaining trace,
even if later windows shrink. There is no implicit migration or recovery.
Rejected windows incur no modeled service cost: admission-failure overhead is
out of scope, rather than silently measured as zero physical work.

`summary.csv` reports requested, served and unserved queries, first failed window,
served windows and maximum required logical memory over the entire trace.
`simulated_partial_total_ms` covers the completed prefix only;
`simulated_total_ms` is blank/null for an incomplete run. Do not rank incomplete
prefixes as cheaper successful executions. The selected site retains its failure
instead of switching to a hindsight winner. The full reference trace still runs
to supply the simulator; it is not evidence that a failed site served requests.

A `passed` manifest means the experiment and correctness checks completed.
`placement_outcomes` separately counts feasible/infeasible/unselected summaries,
including the selected-baseline reference row. It does not mean every candidate
was feasible. Invalid input, accounting overflow or semantic divergence fails
the experiment and retains a failed manifest.

## Evidence and acceptance

| Artifact | Purpose |
| --- | --- |
| `profiles.json`, `planning.csv` | Original assumptions, candidate scores and decision |
| `input.csv`, `workloads.json` | Replayable input and exact request schedules |
| `reference.csv` | Shared oracle checks, cardinalities, payload sizes and host timings |
| `detail.csv` | Per-window accounting and admission outcome for each fixed site |
| `summary.csv` | Fixed baselines and selected baseline, including explicit failures |
| `manifest.json` | Configuration, environment, source/config fingerprints and artifact hashes |

Tests cover hand-calculated compute and transfer costs, one-RTT accounting,
UTF-8 byte sizes, empty answers, expiration-only updates, exact budget boundaries,
late failure without auto-resume, underestimated demand, no feasible candidate,
deterministic selection, malformed/non-finite profiles, overflow, oracle
divergence, replay equivalence and existing-output protection. CI runs a placement
smoke comparison and retains the bundle alongside existing benchmark artifacts.
Deterministic modeled summaries/planning must reproduce; measured host timings
are expected to vary. See [reproduction](reproducibility.md).

## Deferred work

No real hardware calibration, remote deployment, migration, checkpoint recovery,
late-event handling, joint materialisation/placement optimizer, API/dashboard,
LLM/Jev integration or thesis application is included. A proposed v0.5 can add a
separately tested failure/recovery contract without changing these baselines.
