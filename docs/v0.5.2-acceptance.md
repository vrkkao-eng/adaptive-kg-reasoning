# v0.5.2: strict recovery evidence acceptance

## Motivation and unchanged behavior

v0.5.1 closed the retained-support correctness gap. Its acceptance gate checked
service outcomes and aggregate counter reconciliation, but several malformed
records still passed: wrong fault/restore locations, moved per-window validation
work, missing zero counters, boolean integer substitutes and inconsistent timing
fields. Regression tests reproduce these gaps without changing worker behavior.
This is a verification gap, not evidence that historical KG answers were wrong.

v0.5.2 strengthens acceptance only. It does not change incremental reasoning,
fault injection, retry policies, checkpoint schema 1, trace identity, resource
admission or the older materialisation/placement experiments. The opt-in flag
and exploratory mode retain their meanings from [v0.5.1](v0.5.1-validation.md).

## Scenario-derived protocol and work

The validator receives queries, fault specifications, retry budget and checkpoint
cadence. Its reference protocol uses only these declared inputs; it neither runs
the worker nor derives expectations from its observed metrics, state or audit.

Every case must have the exact expected ordered events, with required event
fields and exact field types. This includes:

- fault window and before-update/after-update/after-publication boundary;
- recovery target, policy and consecutive retry numbers;
- explicit cold-start reason (`policy` or `no_checkpoint`);
- checkpoint publication windows, including repeated publication after restoration;
- restoration of the latest published cursor;
- consecutive historical replay windows and their recovery target;
- once-only checked service and the correct terminal event.

Checkpoint publication bytes are positive integers, reconciled with detail and
summary byte counters. Sizes depend on the actual KG snapshot, so the protocol
does not predict an absolute byte size or authenticate snapshot contents.

The reference also counts expected update calls, validation work, faults, retries,
cold bootstraps, replayed transitions, publications and loads per current service
window. Each count must agree in detail and summary. Replayed historical work is
charged to its recovery target's detail row. A retry that crashes before applying
a planned cold bootstrap does not count that bootstrap as executed.

`replayed_windows` includes a recovering current-window transition when needed;
`window_replayed` audit events identify only historical windows before the current
one. Those counts are deliberately not equated. Restoring the current cursor
after publication does not reapply current deltas. Hand-checked protocol tests
cover that boundary as well as the engine-to-contract comparisons.

## Typed per-window evidence

All required counters are present non-negative integers, not booleans, floating
numbers or missing fields defaulted to zero. Window indices and checkpoint cursors
use exact integer types; absent checkpoints require an explicit null cursor.
Each served window has a checked state, and its checked-query count equals its
served count exactly. Stopped and subsequent unserved windows have zero checked
queries. Checked-state work equals applied plus loaded states.

Invalid or missing case keys produce `schema_errors` rather than grouping or
arithmetic crashes. Missing, duplicate and unrequested cases still fail.
Unknown/missing audit fields and reordered events fail even when sequence numbers
and global outcome/counter histograms are otherwise unchanged.

## Timing accounting, not performance acceptance

Every required component time in detail and summary is finite and non-negative,
excluding booleans and numeric strings. Detail fields sum to their summary fields.

```text
measured_work_ms = maintenance + query + checkpoint_write + checkpoint_restore
measured_total_ms = measured_work_ms for completed service; null otherwise
measured_recovery_ms = checkpoint_restore + recovery_apply
recovery_apply <= maintenance
```

Recovery apply is a subset, not an additional component in the work total.
Accounting comparisons use `rel_tol=1e-9`, `abs_tol_ms=1e-7` to accommodate
floating accumulation/subtraction. They never repair metrics or excuse negative/
non-finite values. These tolerances are separate from semantic support-total
tolerances, and are not latency targets, speedup thresholds, RTOs or SLAs.

## Reports, compatibility and CI

`acceptance.json` retains report schema 1 and identifies
`feasible-bounded-worker-recovery-v2`. It records checkpoint cadence, timing
tolerances, schema errors and per-case mismatches. Invalid observed summary
scalars are represented diagnostically so the report can be serialized with
`allow_nan=False`. Original result/audit files remain evidence, not repaired data.

The CLI passes its actual cadence to acceptance. Results are written before the
gate; failed acceptance retains them and a hashed failed manifest, returning a
non-zero exit code. The version label is now v0.5.2. The existing CI job runs the
same feasible 1,000-event matrix, with no new dependency or benchmark workload.

```sh
python experiments/run_v0_5_recovery.py --events 1000 --width 120 --slide 30 --flush --require-expected-outcomes --output-dir results/runs/acceptance-example
```

Valid replay reports stay deterministic despite host timing differences, because
raw timings are not copied into the successful acceptance report. Checkpoint
bytes, non-timing summaries, schedules and audit events retain their deterministic
replay contract. Historical reports still identify their earlier acceptance
contract; they are not silently rewritten.

This remains a local, fixed-trace worker experiment with a surviving coordinator
and end-of-run audit persistence. It introduces no process-kill resume, durable
acknowledgment, append-only audit, dashboard, provider, agent or deployed API.
